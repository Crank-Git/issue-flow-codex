# Epic 3 batch-gate live run, 2026-11-03

This report records the live proof of the deferred criteria M1 to M11 of epic #4 (loop operations).
The run used `Crank-Git/issue-flow-codex-testbed` only. The plugin came from branch `epic/4-loop-operations` (head `95e46d2` plus this harness).
The harness is `tests/e2e/run_loop.py`. It needs `ISSUE_FLOW_E2E=1`, and `unittest discover` skips it.

Result: 10 of 11 criteria pass, and M11 fails on its strict reading (12 of 13 timeouts got a sweep). The run found six port defects, listed at the end. It fixed none of them.

- Isolated `CODEX_HOME`. `auth.json` is a symlink to the operator file. `~/.codex` was not changed.

The harness writes both files before `setup_project.py apply`, because the thread count depends on `concurrency`.

- Evidence sources: the `--json` stream, the rollout files under the isolated `CODEX_HOME/sessions/2026/11/03` (`run_loop.py timeline`, `run_loop.py show`), the tracker, and the CI runs of the test bed. Times are UTC.

## Port defects found (not fixed)

1. `scripts/testbed-reset.py:221-224` (`ensure`). The script reopens a closed seed issue but keeps its old labels and body. After one gate run, the next reset leaves `status:batched` on the members and a stale `issue-flow:begin` batch block in the epic body, so the PM finds no ready issue. Expected: the seed labels and body come back, as for a new issue. The harness works around it (`restore_seed_issues()`).
2. `skills/issue-flow/SKILL.md:653-656` (verdict section, step 2). Expected: a Stage A0 sweep after every timeout. Observed: 1 of 13 timeouts had no tracker read (M11), and the sweeps were single-issue reads. This is defect 2 of the Epic 2 report, still present. `guard-wait.py` fixes the timeout value only.
3. `scripts/setup_project.py:187-190` (role check) against `skills/issue-flow/SKILL.md:141-144` (Phase 0 step 3). The check demands byte-equal role files, and no code reads `workerModel` or `workerEffort` from `.issue-flow.codex.json` (`grep -rn workerModel skills hooks scripts` finds only the docs). The PM shows "workers gpt-6-luna, low effort" in the question, but the role file alone decides the model. A project cannot change the worker model through the config file, and an edit of the role copy makes Phase 0 stop. Expected: either the PM passes the configured model (SKILL line 54 forbids it) or the config keys do not appear in the question.
4. `scripts/setup_project.py:96-97` and `:196-198`. The thread count is `concurrency + THREAD_OVERHEAD` from `.issue-flow.json` at the time of `apply`. Changing `concurrency` later (the PM may do so in step 11) makes the next check report `stale`. Observed in attempt 1 (7 against 6) and in a probe with `concurrency 1` (6 against 5). Expected: the PM tells the operator to run setup again, or the check tolerates a lower value.
5. `skills/issue-flow/SKILL.md` Phase 0, same-login step. The PM asked a question about a second session of the same login in turn 1 of probe M10 and needed two replies ("ok", "ok") before the configuration was confirmed and the loop started. Main attempt 3 needed one. Not a defect by itself, but a harness that sends one reply stalls. The harness now has `run_loop.py resume`.
6. `.issue-flow.json` `pluginVersion`. The Codex PM stamps `0.1.0`, while the config schema and the upstream drift check use the upstream plugin version (the seed file says `0.17.0`). The upstream preflight did not complain (M9). Low priority; record it for Epic 4.
